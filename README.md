# IPtable

IPtable - простое веб-приложение для учета IP-адресов и устройств в локальной сети.
Создавайте папки и подсети, заполняйте данные об устройствах и отслеживайте их
доступность. Вся информация хранится в PostgreSQL вместо разрозненных Excel-файлов.

## Возможности

- Папки и подсети с автоматическим списком IP-адресов.
- Hostname, OS, Type, Comment и собственные столбцы с настройкой типа и порядка.
- Проверка доступности по ping сразу после создания подсети и по расписанию.
- Поиск по всем подсетям, фильтры по ping, OS и Type.
- Скрытие пустых адресов, удобное редактирование и история изменений.
- Импорт и экспорт CSV/XLSX, экспорт папки в архив с возможностью задать пароль.
- Пользователи и права доступа через админ-панель.
- Русский и английский интерфейс, REST API для интеграций.

## Установка

Нужны Git, Docker и Docker Compose. **Все настройки запуска вашей установки
задавайте в `.env`.** Используйте `docker-compose.yml` из репозитория как есть.

### 1. Скачайте проект и создайте `.env`

```bash
git clone https://github.com/lasnet/IPTable.git
cd IPTable
cp .env.example .env
chmod 600 .env
```

Права `600` дают владельцу файла доступ на чтение и запись. `.env` хранит
секреты открытым текстом. Для проверки конфигурации используйте
`docker compose config -q`, чтобы значения секретов не выводились в терминал.

В `.env.example` есть строки для HTTP, обоих вариантов HTTPS и расширенных
настроек запуска. Для включения необязательного параметра уберите `#` перед
его именем и задайте нужное значение. Если `.env` уже существует, сохраните свои
пароли и настройки. Недостающие строки можно скопировать из нового шаблона,
а для уже заданного параметра достаточно поменять значение в его строке.

### 2. Задайте пароли и выберите адрес

| Параметр | Что указать |
| --- | --- |
| `POSTGRES_PASSWORD` | Отдельный пароль встроенной базы PostgreSQL. |
| `INITIAL_ADMIN_PASSWORD` | Пароль для первого входа под `admin`, от 12 символов. |

Логин первого администратора (`INITIAL_ADMIN_USERNAME`) по умолчанию `admin`.
Начальный язык — английский (`INTERFACE_LANGUAGE=EN`), тема — синяя
(`INTERFACE_THEME=blue`).

Для доступа на самом сервере подходят `APP_PORT=8000` и `APP_BIND_ADDRESS=127.0.0.1`.
Оставьте `APP_PUBLIC_URL` закомментированным. Compose подставит `http://localhost`
с портом из `APP_PORT`.
Если IPTable установлен на отдельном сервере, выберите ниже способ доступа по HTTPS.
Для прямого HTTP в изолированной доверенной сети укажите IP хоста Docker
в `APP_BIND_ADDRESS` и раскомментируйте `APP_PUBLIC_URL` в `.env`.

```dotenv
APP_BIND_ADDRESS=192.168.10.10
APP_PORT=8000
APP_PUBLIC_URL=http://192.168.10.10:8000
```

В таком режиме откройте `http://192.168.10.10:8000`. HTTP передаёт пароли,
cookie и инвентаризацию открытым текстом. Храните `.env` на сервере вне Git.

### 3. Запустите IPTable и войдите

```bash
docker compose up -d --build
```

Откройте **http://localhost:8000** на сервере или используйте выбранный сетевой адрес.
Войдите с логином и паролем из `.env`. IPTable автоматически создаёт ключ сессий
на постоянном томе и сохраняет хеш пароля администратора в базе. После успешного
входа удалите строку `INITIAL_ADMIN_PASSWORD` из `.env` и выполните
`docker compose up -d`, чтобы обновить окружение контейнера миграций.

### HTTPS через ваш общий Nginx

На сервере приложения в `.env` измените `APP_BIND_ADDRESS` и раскомментируйте
`APP_PUBLIC_URL` и `TRUSTED_PROXY_IPS`. Для внешнего прокси используйте
`HTTPS_ENABLED=false`, это значение по умолчанию.

```dotenv
HTTPS_ENABLED=false
APP_PUBLIC_URL=https://iptable.example.com
APP_PORT=8000
APP_BIND_ADDRESS=192.168.1.20
TRUSTED_PROXY_IPS=192.168.1.10
```

Встроенный Nginx не нужен. На общем Nginx настройте сертификат и перенаправление
HTTP → HTTPS, а в HTTPS server — upstream приложения:

```nginx
location / {
    proxy_pass http://192.168.1.20:8000;
    proxy_set_header Host $http_host;
    proxy_set_header X-Forwarded-Proto https;
    proxy_set_header X-Forwarded-For $remote_addr;
}
```

Замените адреса своими. `TRUSTED_PROXY_IPS` — IP общего Nginx, видимый контейнеру,
или его доверенная подсеть. Ограничьте доступ к порту приложения этим прокси
через правила сети/Docker firewall. Если прокси на том же хосте, можно задать
`APP_BIND_ADDRESS=127.0.0.1`. Приложение не подключается к прокси само; Secure cookie
и HSTS включаются по `APP_PUBLIC_URL`, остальные production-проверки сохраняются.

### Встроенный HTTPS по выбору

Нужен Docker Compose **2.24.4+**, DNS-имя/IP и выданный для него сертификат.
В `.env` раскомментируйте блок **Built-in HTTPS** и задайте `HTTPS_ENABLED=true`.
В разделе **Network** укажите сетевой IP хоста Docker в `APP_BIND_ADDRESS`
и раскомментируйте `APP_PUBLIC_URL`. Ниже пример итоговых значений этих строк.

```dotenv
HTTPS_ENABLED=true
APP_BIND_ADDRESS=192.168.1.20
COMPOSE_PATH_SEPARATOR=:
COMPOSE_FILE=docker-compose.yml:deploy/https/${HTTPS_ENABLED:-false}.yml
APP_PUBLIC_URL=https://iptable.example.com
APP_PORT=8000
HTTPS_PORT=443
TLS_CERT_FILE=/srv/iptable/tls/fullchain.pem
TLS_KEY_FILE=/srv/iptable/tls/privkey.pem
TLS_KEY_GID=0
```

Запуск остаётся прежним: `docker compose up -d --build --remove-orphans`.
`COMPOSE_FILE` подключает дополнительный файл для встроенного HTTPS.
При переносе строк вручную располагайте `HTTPS_ENABLED` перед `COMPOSE_FILE`.
Имя для Nginx и проверки сертификата берётся из `APP_PUBLIC_URL`.
Пути сертификатов абсолютные, на машине Docker Engine. Сертификат — PEM с цепочкой,
ключ — соответствующий PEM без парольной фразы; оба подключаются только для чтения.
Скрипт проверяет читаемость, срок, имя и соответствие ключа сертификату. Nginx
работает с UID 101 и дополнительной группой `TLS_KEY_GID`. Например, для root-owned
ключа с группой root используйте `TLS_KEY_GID=0` и права `640`; не делайте ключ
общедоступным. Родительский каталог не монтируется.

Сертификаты не генерируются автоматически. Для собственного CA добавьте его
публичный корень в доверие клиентских устройств. Для обновления замените файлы
и выполните `docker compose up -d --force-recreate gateway`; это также обновляет
bind mount при атомарной замене файлов. Закрытые ключи в Git не добавляйте.

Приложение доступно на HTTPS-порту, HTTP на `APP_PORT` перенаправляется на
`APP_PUBLIC_URL` с сохранением пути и параметров. HTTP, ошибочно отправленный на
HTTPS-порт, также перенаправляется. Если порт HTTPS не 443, укажите его и в URL,
например `https://iptable.example.com:8443`. Версия Nginx скрыта в заголовках и
страницах ошибок. Внутренний порт web при этом не публикуется.

Для возврата к HTTP задайте `HTTPS_ENABLED=false` и HTTP `APP_PUBLIC_URL`, затем
`docker compose up -d --build --remove-orphans`: лишний gateway будет удалён.
База и её том сохраняются. После ранее включённого HSTS браузер может продолжать
принудительно использовать HTTPS до истечения политики; изменение конфигурации
не очищает сохранённую браузером политику.

## Настройки

Для портов, HTTPS и подключения к базе продолжайте использовать `.env`.
Если пользователи подключаются напрямую по HTTP и `APP_PUBLIC_URL` задан явно,
при смене `APP_PORT` обновите порт в обоих параметрах. Изменения применяются
командой `docker compose up -d`.

Администратор меняет параметры ping, безопасности, импорта и API-токен
на странице **Настройки**. Приложение хранит эти значения в базе.
Общий интервал ping применяется к новым расписаниям. У существующих папок и
подсетей остаются свои расписания.

Раздел **Настройки → Интерфейс** доступен каждому пользователю. В нём можно
выбрать синюю, зелёную или тёмную тему, язык интерфейса и количество строк
на странице таблицы. Выбор хранится в аккаунте и действует после повторного входа.
Вариант «По умолчанию» использует общие значения установки, включая значения,
сохранённые до перехода на личные настройки. Остальные разделы видит только
администратор. Общее число строк задаётся в разделе **Настройки → Система**.
Название приложения и остальные общие параметры интерфейса можно задать
с сервера командой `app.manage settings set --group interface`.

### Расширенные параметры запуска

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `POSTGRES_USER` / `POSTGRES_DB` | `iptable` | Пользователь и название базы. |
| `POSTGRES_APP_USER` | `auto` | Рабочая роль встроенной базы. При `POSTGRES_USER=iptable` это `iptable_app`. |
| `MAX_REQUEST_BODY_BYTES` | `3145728` | Предел тела HTTP-запроса в приложении и встроенном Nginx, включая поля формы. |
| `DATABASE_URL` | пусто | Подключение приложения к внешней PostgreSQL. |
| `MIGRATION_DATABASE_URL` | пусто | Отдельное подключение для миграций внешней PostgreSQL с правами управления схемой. |

Во встроенной PostgreSQL сервис `migrate` автоматически создаёт отдельную роль
web/worker с правами чтения и изменения таблиц и использования sequences.
Административный пароль БД получают PostgreSQL и migrate. Пароль рабочей роли
вычисляется из ключа установки. Для смены пароля административной роли измените
его в PostgreSQL и укажите то же значение в `POSTGRES_PASSWORD`.

Для внешней PostgreSQL задавайте `DATABASE_URL` рабочей роли и отдельный
`MIGRATION_DATABASE_URL` владельца схемы. Выдайте рабочей роли DML и sequence grants
на таблицы приложения, включая default privileges для будущих миграций.
Production web/worker проверяют отсутствие SUPERUSER, CREATEDB, CREATEROLE,
REPLICATION и BYPASSRLS при запуске. Compose также запускает встроенный
`postgres`. Для резервного копирования внешней БД используйте её инструменты
и сохраните ключ установки отдельно.

Login rate limit глобально удаляет просроченные события независимо от имени
пользователя. Хранилище ограничено 10 000 событиями; при заполнении новые попытки
получают HTTP 429 до освобождения места по сроку хранения.

Чтобы сменить пароль администратора, откройте его профиль в разделе
**Пользователи**. Для восстановления доступа с сервера выполните
`docker compose exec web python -m app.manage reset-admin-password` и введите
новый пароль дважды. В разделе **Пользователи** администратор также может
просмотреть историю изменений IP-адресов и изменить права аккаунта.
Во вкладке «Роли» доступны «Администратор» для полного доступа, «Пользователь»
для просмотра и «Редактор» с правами создавать, редактировать, удалять объекты
и управлять столбцами. Свои роли можно собрать из этих четырёх прав.
Чтобы удалить пользовательскую роль, сначала назначьте другую роль всем
аккаунтам, которые её используют.
Управление пользователями, ролями и общими настройками доступно администраторам.
При обновлении аккаунты сохраняют права, а для нестандартных наборов создаются
отдельные роли.
Выход отзывает текущую сессию. Смена пароля или отключение аккаунта отзывает
все его сессии.

### REST API для интеграций

Создайте токен в **Настройки → Интеграции**. Скопируйте его при создании и
передавайте в заголовке `Authorization: Bearer`. Пока токен отсутствует, API выключен.

```bash
curl -H "Authorization: Bearer $IPTABLE_TOKEN" https://iptable.example.com/api/v1/projects
```

Здесь `$IPTABLE_TOKEN` — токен в окружении вашего скрипта. Замените адрес на
адрес вашей установки. `GET /api/v1/folders` возвращает папки,
`GET /api/v1/projects/{project_id}/addresses` — адреса и их `id`,
`PATCH /api/v1/projects/{project_id}/addresses/{ip_id}` меняет поля адреса,
а `POST /api/v1/projects/{project_id}/ping` запускает проверку подсети.

## Первые шаги

Создайте папку, добавьте подсеть, например `192.168.1.0/24`,
и нажмите «Показать скрытые». Нажмите на строку IP, выберите «Редактировать»
и заполните данные устройства. Статусы ping: `NoTest` - еще не проверялся,
`OK` - доступен, `NO` - не отвечает.

Строку может редактировать один пользователь за раз. Остальные могут её
просматривать и видят логин редактора. Блокировка снимается после сохранения
или закрытия карточки и автоматически истекает, если вкладка перестаёт
её продлевать.
Фоновое продление блокировки не продлевает сессию. Если состав или типы
пользовательских столбцов изменились, откройте карточку заново перед сохранением.

В меню подсети откройте «Столбцы», чтобы скрыть ненужные столбцы в своей таблице.
Видимость сохраняется отдельно для каждого аккаунта и подсети. Скрытые значения
по-прежнему доступны в карточке IP.
Администратор может скрыть столбцы для всех пользователей подсети в разделе
«Видимость для всех». После возврата столбца снова действуют личные настройки.

Для импорта используйте CSV с разделителем `;` или XLSX (обычный или Strict Open XML)
с колонками `ip;hostname;os;type;comment`. Строка заголовка необязательна.
Укажите CIDR, если известен размер подсети. При пустом поле приложение выбирает
наименьшую подсеть, охватывающую все IP из файла. Импорт заполняет весь диапазон
хостов, оставляя отсутствующие в файле адреса пустыми. Network и broadcast
пропускаются. В одной папке можно создать только одну подсеть с заданным CIDR.

История показывает создание, изменение и удаление папок и подсетей, импорт с именем файла
и изменения IP-записей. Записи сохраняются после удаления объектов. Администратор может
скачать CSV за последние 1, 7, 30 или 90 дней либо за всё время. Выгрузка учитывает
открытую папку, подсеть или IP и текущий поиск. Время в CSV указано в UTC.

## Обновление и основные команды

Перед обновлением сохраните `.env` и сделайте резервную копию. Сохраняйте прежнее
имя проекта Compose и тома `postgres_data` и `installation_key`.

При переходе с версии, в которой ключ задавался через `SECRET_KEY`, оставьте его
в `.env` до первого успешного запуска новой версии. Если ключ был указан прямо
в Compose, перенесите его действующее значение в `.env` перед обновлением.
Сервис миграций скопирует его в том `installation_key`. После успешного входа
можно удалить из `.env` `SECRET_KEY` и `INITIAL_ADMIN_PASSWORD` и применить
конфигурацию командой `docker compose up -d`.

```bash
scripts/backup_postgres.sh
docker compose stop web worker
git pull --ff-only
docker compose build --pull
docker compose up -d --no-build --remove-orphans
```

Если в старой установке вы меняли значения прямо в Compose, перенесите их в `.env`
и используйте `docker-compose.yml` из репозитория.
Если обновляетесь с версии, выпущенной до появления веб-настроек, и используете
старые параметры ping, лимитов или токен из `.env`, сначала выполните на новой
версии после сборки и до запуска приложения
`docker compose run --rm --env-from-file .env migrate`. Используйте Docker Compose
с поддержкой `--env-from-file`. Миграция переносит эти значения один раз.
При уже заполненных настройках и токене действуют значения из базы.

```bash
docker compose ps              # состояние сервисов
docker compose logs -f web     # логи приложения
docker compose logs -f worker  # логи ping
docker compose down            # остановка с сохранением базы
```

Скрипт резервного копирования встроенной PostgreSQL создаёт два файла, дамп
`.dump` и ключ `.dump.key`. Храните их вместе с ограниченным доступом.
Для восстановления на той же установке:

```bash
docker compose stop web worker
CONFIRM_RESTORE=YES scripts/restore_postgres.sh backups/имя_копии.dump
docker compose up -d
```

Для восстановления на новом сервере сначала соберите образы (`docker compose build`)
и запустите только PostgreSQL (`docker compose up -d --wait postgres`). Затем выполните
восстановление с двумя файлами и запустите все сервисы. Для старого дампа без `.key`
используйте существующий том ключа или прежний `SECRET_KEY` в `.env`.

Команда `docker compose down` сохраняет тома, а `docker compose down -v` удаляет базу и ключ.
